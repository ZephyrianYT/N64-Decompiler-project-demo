    How to use n64lab
    
    
    n64lab turns N64 machine code into C you can read, then compiles that C into a PC program. The
      Wizard walks you through it. This page explains what each step is doing.
    

    
    The five steps
    
    
      
      
    1. Choose a ROM. Use a ROM you dumped from your own cartridge, or build an example.
        The examples are tiny C programs compiled for the N64, so you can see the whole round trip without a
        commercial ROM.
      2. 
      
    2. Inspect. The header tells n64lab where the code starts (the entry point).
        The CIC is the cartridge's lockout chip: two kinds load the game at a different address, so it
        matters. The checksum is what the console verifies at boot.
      3. 
      
    3. Analyze. Starting at the entry point, n64lab follows every call to find functions,
        every branch to find labels, and every switch to find jump tables. Warnings mean it was
        unsure, e.g. a jump through a register it couldn't resolve.
      4. 
      
    4. Recompile & build. Each MIPS instruction becomes one line of C. The C is
        compiled with the runtime, which pretends to be the N64's hardware: memory, video output, the
        controller.
      5. 
      
    5. Run. On this computer it runs headless and shows the output and last frame. The
        Windows .exe opens a window.
      6. 
    
    

    
    Reading the Explorer
    
    
      
      
    • Registers live in a struct: cpu->a0, cpu->sp, …
        S32(...) means "keep 32 bits, sign-extended", like the real CPU.
      • 
      
    • LW(cpu->sp, 0x14) loads a word from memory at sp + 0x14, through the
        runtime, because the N64 is big-endian and some addresses are hardware.
      • 
      
    • Branches become goto; calls (jal) become C calls;
        jr $ra becomes return.
      • 
      
    • A delay slot is the instruction after a branch. MIPS runs it
        before jumping, so the C puts it first.
      • 
    
    

    
    When a program hangs
    
    
    A hang usually means the program is waiting for hardware n64lab doesn't emulate (an interrupt, the
      RSP, audio). To find where:
    
    
      
      
    1. Rebuild with Track calls ticked.
      2. 
      
    2. Run it. When the time is up, the runtime log shows the stack of functions it was in.
      3. 
      
    3. If it's stuck waiting on a function, stub it in the config with a return value that means
        "ready": {"stubs": {"device_ready": 1}}.
      4. 
    
    
    
    Careful: a stub only returns. It can't do the real function's work, so stubbing something the game
      needs just moves the problem.
    

    
    Config reference
    
    
    
      
    functionsExtra function starts the analyzer can't find, e.g. only reached through a pointer table.
    
      
    names{"0x80001000": "main_loop"}: name functions you've identified.
    
      
    stubsA list of functions to skip, or a map giving each one's return value.
    
      
    segmentsMore code to recompile besides the boot segment, e.g. overlays:
        {"rom": "0xA00000", "vram": "0x80400000", "size": "0x20000"}.
    
    
    

    
    What won't work (yet)
    
    
    Commercial games recompile, but won't play. They need the RSP/RDP graphics and audio processors and
      libultra's threads and interrupts, which this runtime doesn't emulate. docs/LEARNING.md in
      the repository explains each one. That's the best next read.
    

    
    Command line and Docker
    
    
    Everything here is also on the command line: python -m n64lab --help. To run this UI in
      Docker: docker run --rm -p 8064:8064 -v "$PWD:/work" n64lab ui --host 0.0.0.0.
    
    
    Only use ROMs you own. Generated code contains the game's code, so don't share it.
